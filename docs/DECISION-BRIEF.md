# 一、ANR 是什么，为什么要单独采

## 现象

**ANR = Application Not Responding（应用无响应）。**

Android 上有系统弹窗「应用无响应，是否关闭」，用户看得见。**iOS 没有这个弹窗**。iOS 上的对应现象是：

1. 主线程被某个操作卡住（死循环、同步 IO、锁等待、大量布局计算）
2. 界面停止刷新，点击无反应，转圈也停住
3. 卡住超过大约 10 秒（前台），系统 watchdog 直接 `SIGKILL` 杀掉进程

**用户感知是「闪退」，但崩溃平台里一条崩溃都没有**——因为进程不是崩溃死的，是被系统杀的，没有任何崩溃回调机会。

这就是为什么 ANR 必须单独采集：它产生的是"数据黑洞"，用户在客服渠道投诉卡死/闪退，我们在崩溃列表里什么都查不到。

## 为什么难

主线程卡住的时候，**主线程自己没法报告这件事**——它正卡着。所以必须有一个**旁路线程**在外部观察主线程。

三条路线，区别就在于「旁路线程怎么判断主线程卡了」。

## 路线 A：独立线程 semaphore ping

**机制**（我们现在的实现，也是 Sentry `SentryHangTracker` 的做法）：

```
后台线程循环：
  1. 创建一个信号量（初始 0）
  2. DispatchQueue.main.async { semaphore.signal() }   ← 往主线程扔一个空 block
  3. semaphore.wait(timeout: 0.25s)
       成功  → 主线程 250ms 内执行了空 block，说明没卡，重新计时
       超时  → 主线程 250ms 没空，开始每 50ms 采样一次主线程堆栈
  4. 持续超时超过阈值 → 判定为卡顿事件，上报堆栈
```

**代价（可量化）**：每 250ms 向主线程投递一个空 block。这个 block 只做一次 `signal()`，执行时间在微秒级。相当于每秒给主线程增加 4 次 context switch。

**覆盖范围**：**任何原因**的主线程阻塞。包括 `while true {}` 这种纯计算死循环——因为主线程确实没机会执行那个空 block。

**缺陷**：250ms 以下的卡顿检测不到（受阈值限制，可调小但会增加投递频率）。

## 路线 B：RunLoop Observer

**机制**（Matrix `WCCrashBlockMonitorPlugin` 的做法）：

```
向主线程 RunLoop 注册 CFRunLoopObserver：
  监听 kCFRunLoopBeforeSources （即将处理 source/timer 事件）
  监听 kCFRunLoopAfterWaiting  （刚从睡眠中醒来）
在 BeforeSources 记下时刻 T1，在 AfterWaiting 记下时刻 T2
  如果 T2 - T1 超过阈值 → 这一段执行太久 → 判定卡顿
```

**代价**：不向主线程投递任何东西，observer 回调本身极轻。比 A 省电。

**覆盖缺口（关键）**：主线程如果卡在 `while true { heavyCompute() }`，RunLoop 停留在当前这一轮，**永远不会进入下一轮的 BeforeSources/AfterWaiting**，observer 不触发。也就是说：**纯计算死循环这种最严重的卡顿，B 检测不到**，需要额外兜底（比如再用一个低频 ping）。

## 路线 C：编译期插桩

**机制**：编译期改写代码，在每个方法入口/出口插入时间戳，记录每个方法耗时（Matrix TraceCanary 在 Android 上用字节码插桩实现）。

**iOS 上的可行性**：只能用 `-finstrument-functions`。Release 下每次函数调用都要回调两次，开销不可接受；且拿不到有意义的符号。**iOS 上这条路不成立**。

## 三家实际选择

| | Sentry | Matrix (iOS) | Matrix (Android) | Firebase |
|---|---|---|---|---|
| 路线 | A | B | C | 不做 |
| 能抓死循环 | ✅ | ❌（需兜底） | ✅ | — |
| 主线程额外开销 | 每秒 4 次空 block | 无 | 每方法 2 次回调 | — |

## 选它的后果

| 选择 | 得到 | 失去 |
|---|---|---|
| **A（维持现状）** | 死循环也能抓；口径与 Sentry 一致，便于对标 | 每秒 4 次主线程调度；需要实测确认对启动/长列表无可测影响 |
| **B** | 更省电，主线程更干净 | 抓不到纯计算死循环——而这恰恰是最需要事后定位的那类 |
| **A+B 混合** | 平时走 B 省电，B 沉默超过阈值再用 A 兜底 | 两套逻辑都要维护，且两条路都出错时更难定位 |

**我的建议**：A。理由只有一个——B 漏掉的正是最严重的场景。如果担心耗电，可以调大 ping 间隔（250ms → 500ms），代价是检测粒度变粗。

# 二、OOM 要做到多深

## 现象

系统因内存不足杀掉进程（jetsam）。**同样是 SIGKILL，没有崩溃日志**，用户看到"闪退"。

## 三条路线

### A. MetricKit `MXAppExitMetric`（系统权威）

- 系统给出四类退出统计：`memoryLimitExceeded` / `appWatchdog` / `memoryPressure` / `abnormal`，**累计计数**（要用增量，不是绝对值）
- 限制：**iOS 14+**；**次日批量投递**；用户关闭「共享 iPhone 分析」后**永远不会到达**
- 代价：零（系统自己做的）

### B. 启发式现场（下次启动推断）

- 每次启动时读上次落的 `app_state.json`，看：是否走了 `willTerminate`（干净退出）、最大卡顿时长、内存爬升序列、是否收到内存警告、是否有未结束的后台任务
- 覆盖：**全版本、全用户**
- 限制：只能给「证据」，不能给「权威结论」。用户上划强杀、越狱插件杀进程，在本地和 OOM 无法区分
- 代价：每 5s 一次落盘（原子写，后台队列）

### C. malloc 分配记录（Matrix `WCMemoryStatPlugin`）

- hook `malloc`/`free`/`calloc`/`realloc`，每次分配记录「大小 + 分配栈」，OOM 时把分配快照上报
- 能得到：**哪个对象、哪行代码分配的、占了多少**
- 代价（这是重点）：
  - 每次 malloc 都要 backtrace 一次取栈。单次 backtrace 约 1–10μs，一个 App 启动阶段 malloc 次数是百万级——**启动耗时会明显上升**
  - 要处理递归分配（hook 内部自己也会 malloc）、多线程竞争、锁重入
  - 快照体积大，需要裁剪和压缩
  - 这是三个能力里工程量最大的一个（Matrix 里是独立 plugin，代码量可观）

## 三家

| | Sentry | Matrix | Apple |
|---|---|---|---|
| 路线 | 只做 B，且**明确排除**强杀/调试器/模拟器/OS 升级/app 升级/首启 | C | A |

## 选它的后果

| 选择 | 得到 | 失去 / 代价 |
|---|---|---|
| **A+B 双源（现状）** | 全版本有数据（B）+ iOS14+ 有权威数据（A）；两条都带 `attribution` 标记，可用计数差反推 MetricKit 覆盖率 | 覆盖率不是 100%；B 在强杀场景会给出 `unknown_unclean`（**故意不猜**） |
| **A+B+C** | 能定位到具体分配点，真正做到"知道为什么会 OOM" | 启动耗时上升；工程量最大；需要长期调优 |
| **只 A** | 口径最权威 | iOS 13 完全无数据；关闭分析的用户全缺；次日才有数据，无实时性 |

**我的建议**：先 A+B（已实现）。C 作为独立阶段评估——它需要单独的性能基线测试，不能和这次改动混在一起。

# 三、崩溃采集是否自己接管 handler

## 现象与约束

iOS 崩溃捕获靠注册 `signal handler`（SIGSEGV/SIGABRT 等）和 `NSUncaughtExceptionHandler`。

**关键约束**：同一个 signal 只能有一个"生效"的 handler。后注册的会覆盖先注册的（或形成一条链，链条越长越容易在崩溃瞬间出问题）。

**我们宿主（TBCrashReporter）已经注册了一套。** SDK 再注册，就会顶掉它。

## 两条路线

### A. 不接管（现状）

- SDK 完全不碰 signal，只依赖宿主把崩溃落成 JSON 文件，SDK 负责：解析 → 转成标准事件 → 补镜像 UUID → 补上次会话面包屑 → 去重 → 补发
- 好处：零冲突；宿主换 reporter 也不影响 SDK
- 代价：**崩溃捕获能力等价于宿主**，SDK 不改进它。如果宿主的 reporter 抓不全（比如没抓全线程栈），SDK 也补不上

### B. SDK 自己接管（KSCrash 风格）

- SDK 注册自己的 handler，捕获：所有线程栈、寄存器状态、崩溃时的内存信息、更可靠的符号化
- 代价：
  - 必须先**移除宿主的 handler**，否则两者打架。这需要宿主配合改造
  - signal handler 里只能调用 async-signal-safe 函数，写错会在崩溃时死锁或二次崩溃——**这是最容易出人命的代码**
  - 需要长期真机验证

## 三家

Matrix（基于 KSCrash）、Sentry（自研）、Firebase Crashlytics **全部自己接管**。原因很直接：崩溃采集是 APM 的核心能力，没人愿意把它外包给宿主。

**我们例外，是接入约束决定的，不是技术判断。**

## 选它的后果

| 选择 | 得到 | 代价 |
|---|---|---|
| **A（现状）** | 零冲突、可共存、接入成本低 | 崩溃质量取决于宿主；无法保证全线程栈 |
| **B** | 崩溃能力完整自主，能对标 KSCrash | 必须改宿主；signal-safe 代码风险高；需要专门的真机崩溃矩阵测试 |

**我的建议**：短期维持 A，但在文档里写死「崩溃率准确性取决于宿主 reporter」这个事实。中期如果要做到"能力完整可交付"，B 是绕不过去的——因为一个监控 SDK 的崩溃采集依赖别人，这件事本身就说明它还不是一个完整产品。
